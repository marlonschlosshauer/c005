# Notification infrastructure: capabilities and constraints

Research date: 2026-11-13. Code inspected at `979e28535d8b0ddd32b7241e51423c9a381879ad`.
Context: [What infrastructure capabilities and constraints matter for Cadence notifications?](https://github.com/marlonschlosshauer/c005/issues/6), part of [Notification system — decision map](https://github.com/marlonschlosshauer/c005/issues/1).

This is evidence for a later architecture decision, not that decision. Both Knock with Postmark and an application-owned inbox/workflow system with Postmark can support the requested channels. They put different amounts of state and operational work inside Cadence. No third provider is introduced: this investigation found no concrete channel gap requiring one.

The planning scope includes Students, Instructors, Platform Admins, and Team Admins. Purchase notices to instructors, new Refund Request notices to Platform Admins, and Refund Request updates to Students are examples, not a settled catalogue or channel assignment. Whether initial discovery must exhaust every existing product flow remains undecided; this note does not perform that catalogue exercise.

## Existing code: facts

- [Mailer](../../app/lib/mailer.server.ts) uses a plain `fetch` to Postmark `/email`, a fixed sender, plain text, and `outbound` transactional stream. It throws on non-OK HTTP responses but discards the successful response, including Postmark's message identifier. Without `POSTMARK_SERVER_TOKEN`, it writes JSON files under `.outbox`. Those files are a development transport, not a durable job queue or delivery ledger; no replay worker is defined here. [Mailer test](../../app/lib/mailer.server.test.ts) exercises the file transport.
- [Refund submission action](../../app/routes/courses.$slug.refund.ts) calls `raiseRefundRequest` before awaiting email. [Admin refund action](../../app/routes/admin.refunds.tsx) similarly calls the decision function before sending. [Refund service](../../app/lib/refunds.server.ts) constructs buyer-facing receipt/decision email content and changes domain state, including transactional approval/decline updates. **Inference:** a crash or mail failure after the database mutation can leave changed domain state without email; a successful domain mutation is not proof of delivery. A later notification design must account for this boundary under either provider choice.
- [Schema](../../app/db/schema.ts) has numeric stable user IDs, unique email, three platform roles (`student`, `instructor`, `admin`), and separate team membership roles. Team Admin is not a fourth `UserRole`. Courses reference their instructor; purchases and Refund Requests have their own IDs. No notification inbox, delivery ledger, or preference tables exist in this inspected schema.
- [Session](../../app/lib/session.ts), [access guards](../../app/lib/access.server.ts), and the [app layout loader](../../app/routes/layout.app.tsx) provide current-user context. The session uses a development secret and the DevUI switches users. **Inference:** recipient selection and inbox authorization must use server-resolved identity; browser-supplied recipient IDs or role labels are insufficient. Production authentication hardening is a separate dependency, not something Knock supplies for Cadence.
- [Database ADR](../adr/0006-one-sqlite-file-through-drizzle.md) commits the present system to one server process and one SQLite file through Drizzle, with one writer. [Dependencies and scripts](../../package.json) have React 19, React Router 8, Vitest, and no Knock SDK or queue service. [Purchase route](../../app/routes/courses.$slug.purchase.tsx) contains a welcome-email placeholder, not another live mail delivery path. [README](../../README.md) mentions a future Knock Developer account; this is not an implemented integration.

## Reliability, security, and diagnostics

**Knock facts.** Trigger idempotency uses `Idempotency-Key` (maximum 255 characters), normally for 24 hours. Only `POST /workflows/:key/trigger` supports it; successful responses are cached, and changed parameters with the same key cause an error. Rate tiers apply; trigger is Tier 5 (1,000 requests/second). Respect throttling and retry guidance rather than treating unlimited workflow counts as unlimited request throughput. [API overview](https://docs.knock.app/api-reference/overview/openapi), [trigger limits](https://docs.knock.app/api-reference/workflows/trigger).

Knock retries transient provider/network failures up to eight times over 30 minutes with backoff/jitter, records queued/attempted/bounced/undelivered states, exposes provider request/response logs, and allows manual retries of undelivered messages. This is provider delivery handling **after Knock has received the trigger**, not atomic delivery of a Cadence database transaction. [Delivery behavior](https://docs.knock.app/send-notifications/delivering-notifications). Postmark delivery means acceptance by the recipient's mail server, not human reading; Knock can receive delivery/bounce/complaint updates through configured Postmark webhooks. [Integration status definitions](https://docs.knock.app/integrations/email/postmark).

Production client access requires enhanced security mode: backend-generated RS256 user JWTs, subject identity, expiration/refresh handling, and appropriately restricted grants. Mode is off by default. Tenant grants can restrict feed/preference access; a client feed filter alone is not an authorization boundary. Cadence must issue grants from its own membership/access rules. [Client security](https://docs.knock.app/in-app-ui/security-and-authentication).

**Postmark facts.** Postmark does not currently support send idempotency keys. [Idempotency support](https://postmarkapp.com/support/article/what-is-an-idempotency-key). Webhooks are retryable and can arrive repeatedly; current outbound documentation describes six retry delays (1, 5, 10, 10, 10, 15 minutes), retrying network/5xx/408/429 failures and dropping other 4xx failures. Persist event-level deduplication; `MessageID` alone must not collapse distinct delivery, bounce and engagement events. Endpoint protection uses HTTPS, Basic Auth/IP allowlisting and validation; HMAC signatures are not supported. [Webhooks](https://postmarkapp.com/developer/webhooks/webhooks-overview).

**Design options and implications, not decisions.** A transactionally written event/outbox record with a restart-safe dispatcher is one way to bridge domain commit to either Knock trigger or direct Postmark submission. A uniqueness constraint on event/recipient/channel can stop local duplicate work. It cannot prove exactly-once external email when a provider accepts a send but its response is lost: Postmark lacks idempotency, and Knock's trigger window is finite. Decide acceptable duplicate/loss behavior, retry duration, recovery tools and retention before writing acceptance criteria. Avoid claiming end-to-end exactly-once delivery.

For either path Cadence still owns event meaning, recipient eligibility (including overlapping roles), domain transaction boundaries, authorization of action destinations, audit correlation, and failure policy. With app-owned workflows it additionally owns job scheduling/recovery, retry classification, email/webhook correlation, inbox state and operational tooling. With Knock it additionally operates user/profile synchronization, workflow versions, provider configuration, signed frontend tokens and a cross-system diagnostic trail.

## Development and testing

Knock supports isolated environments and workflow versioning. Its test runner can force sandbox delivery and skip delays, works on the latest saved workflow, and bypasses trigger-frequency restrictions; production API calls use the committed workflow. CLI and API can run tests too. **Implication:** validate frequency/idempotency through real trigger API tests, not only the dashboard runner. [Workflow tests](https://docs.knock.app/send-notifications/testing-workflows), [platform tools](https://docs.knock.app/getting-started/knocks-features).

For direct Postmark, `POSTMARK_API_TEST` validates requests without delivery. Sandbox servers exercise activity APIs/webhooks without reaching inboxes, but **count toward monthly sending volume**, and server type cannot later be changed. [API testing](https://postmarkapp.com/developer/user-guide/send-email-with-api), [sandbox servers](https://postmarkapp.com/developer/user-guide/sandbox-mode/server-sandbox-mode).

Existing injected `MailTransport` and `.outbox` remain useful test seams. Neither validates live sender setup, production credentials, retry recovery, tenant/user isolation or actual deliverability. A future implementation's meaningful checks would include role/ownership isolation, duplicate event replay, crash-after-commit recovery, preferences, provider rejection, duplicate webhooks, and switching users without retained feed state. These are suggested verification areas, not an agreed acceptance suite. No provider account was provisioned and no live sends or SDK compatibility tests were performed for this research.

## Data boundaries and deletion

- Knock stores recipient profiles, preferences, workflow payloads/messages and feed engagement. Standard log retention is 30 days, Enterprise 90; API logs are universally 30 days. **Feed notifications remain available indefinitely after log expiry**, so diagnostic retention is not inbox deletion. Custom log retention is not currently supported by the published retention docs. [Retention](https://docs.knock.app/manage-your-account/data-retention).
- Knock's user-delete API hard-deletes user properties, preferences, subscriptions, schedules, messages and associated logs, potentially taking ten minutes. Reusing that ID creates a fresh user. This does not delete Postmark's independent copy or email already delivered to a recipient. [User deletion](https://docs.knock.app/managing-recipients/deleting-users).
- Postmark defaults to 45 days of content/activity retention. The retention add-on supports 7–365 days on eligible paid plans; expired data is queued for deletion, with documented processing lag. [Retention add-on](https://postmarkapp.com/support/article/how-does-the-retention-add-on-work). Its account-level recipient Data Removal API is available **by request only** through support. [Data removal](https://postmarkapp.com/developer/api/data-removals-api).
- App ownership can keep inbox/profile/preference state local but still sends email content/addresses to Postmark. Cadence owns local deletion, backups and `.outbox` cleanup in either design. Minimize provider payloads; a Refund Request's full free-text reason need not be included merely because a template can receive it. This is a minimization option, not a content decision.
- Required geographic storage, contractual terms, deletion SLA and retention periods are **unknown product/operational requirements**. This investigation does not establish an EU-only hosting commitment or account-specific deletion guarantees for either service; confirm with provider contracts/support if required.

Knock bills each successfully sent user/channel message: one event to one recipient via inbox and email is two messages; failed/bounced messages are excluded. [Knock usage](https://docs.knock.app/manage-your-account/knock-plans). Neither totals nor savings can be estimated without event frequency, recipient fan-out, channel selection, suppression/batching policies and volume.
